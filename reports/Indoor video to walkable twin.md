# Keep the pipeline, fix four weak links

The team's pipeline is the right architecture and will mostly work, but four links will probably fail or underperform on a 5-8 minute multi-room walk. **First, COLMAP sequential matching as nerfstudio 1.1.5 runs it has no loop detection**, so the camera path will drift and can split into several models at doorways, and nerfstudio silently trains only on `sparse/0`. **Second, splatfacto's default densification has no Gaussian cap**, so a large multi-room scene risks running out of memory late in training on 8 GB. **Third, the navgrid builds obstacles only from splat centers.** That makes it sensitive to floaters, gaps between large wall Gaussians, and "rooms behind mirrors". **Fourth, GaussianSplats3D is abandoned**: its author now points users to Spark, and an uncompressed 32 B/splat `.splat` file is 3-6x larger than it needs to be. Every fix is incremental. Run COLMAP yourself with loop detection, or run COLMAP 4.2.1's global mapper side by side, and import the result with `--skip-colmap`. Train splatfacto with CPU image caching, bilateral grid and scale regularization. Harden the grid with ray carving from the training cameras and a manual wall brush. Swap the viewer to Spark 2.4 and serve SOG files. Commercial apps are useful only as disclosed sensor loggers or benchmarks. Using one as the core reconstruction is a serious rule risk, because the brief requires a repository that rebuilds the model. None of these pipelines has been run end to end on the target laptop, so every timing below is an estimate unless it is marked as measured or verified.

## Sequential COLMAP without loop closure is the most likely failure

Pose estimation is where a long multi-room walk breaks first. nerfstudio's `run_colmap` passes only single-camera, camera-model and GPU flags to COLMAP. It passes **no `SequentialMatching.loop_detection` and no overlap setting**, and it reads only `colmap/sparse/0` ([nerfstudio colmap_utils.py](https://raw.githubusercontent.com/nerfstudio-project/nerfstudio/main/nerfstudio/process_data/colmap_utils.py); [converter defaults](https://raw.githubusercontent.com/nerfstudio-project/nerfstudio/main/nerfstudio/process_data/colmap_converter_to_nerfstudio_dataset.py)). On video sequences, COLMAP "can generate multiple models due to failed image registration" ([arXiv 2504.20496](https://arxiv.org/pdf/2504.20496)). Indoor scenes make this worse, because large plain walls, ceilings and floors leave SfM with few reliable points ([IM360, arXiv 2502.12545](https://arxiv.org/pdf/2502.12545)). Version 3.9.1 also has the sequential-overlap bug that COLMAP 3.11.0 fixed: the matcher always skipped the farthest image ([COLMAP changelog](https://colmap.github.io/changelog.html)). Ironically, nerfstudio's default `vocab_tree` matching gives some loop closure and still works on 3.9.1, because its FLANN tree predates COLMAP 3.12's switch to faiss. The team gave that up by choosing `sequential`.

The cheapest fix keeps COLMAP 3.9.1 and runs it by hand. Use `feature_extractor --ImageReader.single_camera 1 --ImageReader.camera_model OPENCV --SiftExtraction.use_gpu 1`. Follow it with `sequential_matcher --SequentialMatching.overlap 20 --SequentialMatching.quadratic_overlap 1 --SequentialMatching.loop_detection 1 --SequentialMatching.vocab_tree_path vocab_tree_flickr100K_words32K.bin --SiftMatching.use_gpu 1`. Then run `mapper` and `bundle_adjuster`, and import the model with `ns-process-data images --data out/images --output-dir out --skip-colmap --colmap-model-path colmap/sparse/0`. With about 350 frames, `exhaustive_matcher` is a feasible and more robust fallback. The notes estimate tens of minutes for it on the 4070; that is an estimate, not a measurement. Check every run with `colmap model_analyzer` and confirm there is exactly one model with most frames registered. OPENCV versus SIMPLE_RADIAL for phone lenses is an untested judgement call; SIMPLE_RADIAL is safer if registration is shaky.

The stronger upgrade is COLMAP 4.2.1 (Sep 2026), installed side by side and kept off the PATH. It ships GLOMAP as `global_mapper`, and since 4.2.0 it **reconstructs every disconnected component** instead of silently dropping all but the largest. It also adds ALIKED+LightGlue and LoMa learned matching through ONNX and ships Windows binaries ([COLMAP changelog](https://colmap.github.io/changelog.html); [radiancefields.com on 4.2](https://radiancefields.com/colmap-4.2.0-adds-multi-component-global-mapping-and-loma-learned-matching)). An independent March 2026 ETH3D benchmark puts GLOMAP level with incremental COLMAP: **77.28% vs 77.39%** of views within 1°/5 cm, in **64.8 s vs 87.5 s** ([arXiv 2603.20428](https://arxiv.org/html/2603.20428v2)). Do not point ns-process-data at the 4.x binary. Version 4.1.1 renamed the flags to `FeatureExtraction.*` and `FeatureMatching.*`, while nerfstudio still hard-codes the `Sift*` names and loads the old FLANN tree. The 4.x recipe is `feature_extractor ... --FeatureExtraction.use_gpu 1`, then `sequential_matcher --SequentialMatching.overlap 20 --SequentialMatching.loop_detection 1 --FeatureMatching.use_gpu 1` (the faiss vocab tree downloads automatically), then `global_mapper`, then `--skip-colmap`. Confirm the option names with `colmap <cmd> -h`. Global SfM can hide trajectory breaks, so inspect the result in `colmap gui`.

The other options are fallbacks. hloc (SuperPoint+LightGlue) is supported by nerfstudio, but it depends on pycolmap, which "is currently not supported" for Windows source builds. It is the riskiest install, and COLMAP 4.x's native learned matchers cover most of its benefit ([pycolmap README](https://github.com/mihaidusmanu/pycolmap)). Feed-forward models are not yet a replacement. On ETH3D, VGGT reaches **10.80%** of views within 1°/5 cm against COLMAP's 77.39%. Vanilla VGGT needs **21 GB at 100 frames** ([arXiv 2603.20428](https://arxiv.org/html/2603.20428v2); [VGGT-X](https://arxiv.org/html/2509.25191v2)), and even chunked VGGT-X used about 9.7 GB for about 300 frames. The best result in that benchmark came from feed-forward initialization followed by classical matching and bundle adjustment. VGGT's `demo_colmap.py --use_ba` exports COLMAP files that gsplat can use ([VGGT GitHub](https://github.com/facebookresearch/vggt)). Treat it as Fallback C, in a separate virtual environment, used only if textureless stretches defeat SIFT. The most robust pose source of all comes from the phone's own sensors. **Polycam raw export (LiDAR iPhone, Developer mode), Record3D (iPhone 12 Pro or newer) and KIRI's "Camera pose" mode (Android or iOS, no LiDAR)** all feed nerfstudio directly ([nerfstudio custom data docs](https://docs.nerf.studio/quickstart/custom_dataset.html)), and AR poses carry metric scale. Capture discipline costs nothing and probably matters more than any flag: walk slowly, lock exposure, linger at doorways, avoid filling the frame with blank walls, and finish the walk in the room where it started.

## Splatfacto is the safe default; a capped MCMC run is the better one

Several facts here were **verified directly on the team's machine**. The `.venv-ns` environment runs Python 3.10.18, torch 2.1.2+cu118, gsplat 1.4.0+pt21cu118 and nerfstudio 1.1.5 on an 8188 MiB RTX 4070 Laptop. **nerfstudio 1.1.5 has no `splatfacto-mcmc`**: `SplatfactoModel` hard-codes `DefaultStrategy`, although gsplat 1.4.0 itself ships `MCMCStrategy`. The global `pip` on the PATH reports torch 2.9.0, so always call `.venv-ns\Scripts\ns-train.exe` explicitly. Do not upgrade anything. gsplat 1.5.3 dropped Windows cu118 builds ([gsplat releases](https://github.com/nerfstudio-project/gsplat/releases)), and a newer nerfstudio would pull it in.

The memory case for MCMC is clear-cut. On gsplat's own Mip-NeRF 360 ablation, **MCMC capped at 1M Gaussians scores 29.18 PSNR in 1.98 GB, while default densification scores 29.00 PSNR with 3.24M Gaussians in 5.62 GB** ([gsplat eval docs](https://docs.gsplat.studio/main/tests/eval.html)). nerfstudio lists splatfacto at about 6 GB and splatfacto-big at about 12 GB, which rules out the big variant ([nerfstudio splatfacto docs](https://docs.nerf.studio/nerfology/methods/splat.html)). A multi-room scene has a large spatial extent, so uncapped densification is the main OOM risk. The notes expect 2-4M Gaussians, an estimate. MCMC's opacity and scale regularization also removes dead Gaussians, which means fewer floaters for the navgrid. The catch is that MCMC is reachable only through gsplat's `examples/simple_trainer.py` at tag v1.4.0. That script needs `fused-ssim`, a CUDA extension that must compile under MSVC with nvcc 11.8, plus a pycolmap fork and `numpy<2` ([v1.4.0 requirements](https://raw.githubusercontent.com/nerfstudio-project/gsplat/v1.4.0/examples/requirements.txt)).

The default command uses flag names checked against the installed source:

```powershell
.\.venv-ns\Scripts\ns-train.exe splatfacto `
  --max-num-iterations 30000 `
  --pipeline.datamanager.cache-images cpu `
  --pipeline.datamanager.cache-images-type uint8 `
  --pipeline.model.use-bilateral-grid True `
  --pipeline.model.use-scale-regularization True `
  --pipeline.model.camera-optimizer.mode SO3xR3 `
  --vis viewer+tensorboard `
  colmap --data <scene_dir> --downscale-factor 2
```

Each flag has a reason. The bilateral grid absorbs auto-exposure and white-balance shifts between rooms. Scale regularization suppresses spiky Gaussians. CPU caching saves the 1.3-1.7 GB the notes estimate for 350 frames at 1600x900. Keep the default `cull_alpha_thresh 0.1`. nerfstudio's "quality" setting of 0.005 keeps more low-opacity Gaussians, and those floaters pollute the occupancy map. `SO3xR3` pose refinement is not benchmarked here; drop it if training diverges. If memory runs out late in training, add `--pipeline.model.densify-grad-thresh 0.0012 --pipeline.model.stop-split-at 10000`. Export with `ns-export gaussian-splat --load-config <config.yml> --output-dir exports/splat`. The MCMC alternative is `python simple_trainer.py mcmc --data_dir <scene> --data_factor 2 --result_dir results/<scene> --strategy.cap-max 1000000 --use_bilateral_grid --pose_opt --disable_viewer`. Those flag spellings come from the v1.4.0 era and are unverified, so confirm them with `--help`. Leave antialiased mode off: it adds little PSNR and renders incorrectly in classic web viewers.

No RTX 4070 Laptop timings exist. Splatfacto took **8.9 min for 30k iterations on ScanNet++ on an RTX 4090** ([DN-Splatter](https://arxiv.org/html/2403.17822)). Scaling that by about 3x gives an estimated 25-40 min on the laptop at roughly 1000-1200 px. At 7k iterations gsplat reaches 27.21 PSNR in about a sixth of the time it takes to reach 28.95 at 30k, so use 7k runs for quick previews. Brush offers a no-Python Windows backup trainer. It takes COLMAP input, trains MCMC-style with a splat cap, and supports masks for mirrors ([Brush GitHub](https://github.com/ArthurBrussee/brush)), but it has no depth priors. Geometry-focused trainers are not worth the risk for a 2D walkable map. DN-Splatter roughly doubles indoor mesh F-score (**.924 vs .584** for Splatfacto on MuSHRoom), but it has only been tested against gsplat 1.0.0, while plain 2DGS barely improves on Splatfacto (.604) ([DN-Splatter](https://arxiv.org/html/2403.17822)). PGSR, GOF and RaDe-GS all need custom CUDA rasterizers built on Windows, with no documented support.

## The navgrid design is sound, but its obstacles come from the wrong source

Using the camera path as guaranteed free space, a height-band slice and a 2D grid follows the industry pattern. NavGSim (2026) builds its collision map by slicing Gaussians every 10 cm. The difference is that it slices each Gaussian's **full ellipsoid analytically**, not just its center ([NavGSim, arXiv 2603.15186](https://arxiv.org/html/2603.15186)). Center-only slicing ignores extent. Large wall Gaussians leave gaps between their centers, floaters become solid cells in mid-air, and standard 3DGS "often misinterprets reflections as virtual spaces" behind mirrors ([arXiv 2509.18956](https://arxiv.org/html/2509.18956v1)). The flood fill from the camera path already removes splats behind walls, which is a good mitigation. It cannot remove floaters inside the rooms the walk passed through.

The highest-value hardening is free-space carving. gsplat's `rasterization()` renders expected depth with `render_mode="ED"` ([gsplat docs](https://docs.gsplat.studio/main/apis/rasterization.html)). Render that depth from every training pose, cast rays from each camera to its depth, and mark the crossed cells free. Any floater a camera looked through disappears. Around that, the notes recommend several smaller steps (estimated at 1-2 days in total). Stamp each Gaussian's 2σ footprint instead of only its center, and require an opacity-weighted density per cell. Apply morphological open and close, and drop blobs smaller than about 2 cells. Force the camera trajectory, dilated by about 30 cm, to stay free. Inflate obstacles by the agent radius with `scipy.ndimage.distance_transform_edt`, and string-pull the A* paths. Finally, add a small "paint wall / erase" brush in the viewer for mirrors and glass. The heavier option is TSDF fusion: render `RGB+ED` at about 400 poses at half resolution, mask pixels with alpha below 0.5, truncate depth at 4-5 m, and fuse with Open3D `ScalableTSDFVolume` using 0.03 m voxels and a 0.12 m truncation ([Open3D](https://www.open3d.org/docs/release/tutorial/pipelines/rgbd_integration.html)). Fusion averages out geometry that disagrees across views, and the resulting mesh doubles as a three.js occluder. No paper compares center slicing with TSDF head to head, so the gain is expected, not measured. Recast navmeshes through recast-navigation-js (`generateSoloNavMesh`, `computePath`, `exportNavMesh`) make paths look better, but on a single flat floor they add no capability over a 10 cm grid ([recast-navigation-js](https://github.com/isaac-mason/recast-navigation-js)). Add one only if time is left over.

For gravity, keep the floor RANSAC and make it more robust. Seed "up" from the mean camera down vector, then search for the floor only about 1-2 m below the camera path among points whose normals lie within 30° of that seed. Check that the floor and ceiling normals agree within 1-2°. This is engineering judgement; no source quantifies it. Metric scale needs more care than it is getting. Tape error on a 2.7 m ceiling is under 0.5%, but textureless ceilings give fuzzy, offset planes in 3DGS, so the notes estimate the real error at 1-5%. The **1.4 m camera-height prior varies by roughly ±10-15%** with how the phone is held, which makes it a sanity bound only. Better references are two or three horizontal tape measurements between textured features, such as a door-frame width, or an A4 ArUco tag triangulated from the COLMAP poses (expected around 1%, though no source gives a number). Report the median and the spread, and accept agreement within about 3%. Metric-depth models give an independent cross-check: **MoGe-2 scores 4.44% relative error on NYUv2 with known intrinsics and 7.33% without** ([MoGe-2, arXiv 2507.02546](https://arxiv.org/html/2507.02546)). Take the median ratio between its depth and the rendered depth over about 50 frames. Bias across the whole scene remains even after taking the median.

## GaussianSplats3D is abandoned; Spark plus SOG is a few hours' work

The GaussianSplats3D README says it is "no longer in active development" and recommends Spark. Version 0.4.7 (January 2025) is the last release, and its peer dependency targets three r160 ([GitHub](https://github.com/mkkellogg/GaussianSplats3D); [npm](https://registry.npmjs.org/@mkkellogg/gaussian-splats-3d)). **Spark 2.4.0 shipped on 2026-10-20** under the MIT license with peer dependency `three >=0.180.0`, so r186 is supported ([npm](https://registry.npmjs.org/@sparkjsdev/spark)). It loads the team's existing `.splat` file unchanged, as well as `.ply`, `.spz`, `.sog` and streamable `.rad`. It has LoD with a per-device splat budget (500K-2.5M) and a THREE.Raycaster-compatible `SplatMesh.raycast()`. The docs warn that raycasting "should not be called every frame" at millions of splats ([SplatMesh docs](https://sparkjs.dev/docs/splat-mesh/); [Spark 2.0 features](https://sparkjs.dev/docs/new-features-2.0/)). Splats depth-test against opaque meshes but do not write depth ([SparkRenderer docs](https://sparkjs.dev/docs/spark-renderer/)). Draw floor arrows as opaque meshes, and raycast against a floor plane or collision mesh rather than the splats.

For compression, PlayCanvas reports a **4M-Gaussian scene shrinking from a 1 GB PLY to 42 MB of SOG** ([PlayCanvas blog](https://blog.playcanvas.com/playcanvas-open-sources-sog-format-for-gaussian-splatting/)), roughly 10 B/splat including SH. That compares with the 32 B/splat `.splat` the app ships now, which has no SH at all. SPZ is about 10x smaller than PLY ([nianticlabs/spz](https://github.com/nianticlabs/spz)). The splat-transform CLI (MIT) converts between all of these formats and can also filter floaters (`-F`) and strip SH bands (`-H`) ([splat-transform](https://github.com/playcanvas/splat-transform)). The migration is `npm i @sparkjsdev/spark`, then replacing the viewer with `scene.add(new SparkRenderer({renderer}))` and `scene.add(new SplatMesh({url}))`, then running `npx @playcanvas/splat-transform scene.splat scene.sog`. For laptops, set `antialias: false`, cap the pixel ratio at 1.5, set `maxStdDev` to about √5 ([Spark performance docs](https://sparkjs.dev/docs/performance/)), and turn on `lod: true`. Check the scene's orientation after conversion, because the up-axis conventions differ. Moving to PlayCanvas or Babylon would mean rewriting the app outside three.js for no gain within this deadline.

## Commercial apps belong in the benchmark table, not the pipeline

The brief, as the team's notes quote it, asks teams to design "a complete software pipeline", scores "SOP & pipeline soundness", and requires a repository with setup instructions to rebuild the model. A cloud scan cannot be rebuilt from a repository. Making Polycam, Scaniverse, Matterport or Teleport the core is therefore a **high penalty risk**. The public Namma Space rulebook was not indexed online, so this assessment comes from the brief's wording rather than from published rules. Luma is out: its 3D capture product was wound down, with Flythroughs shutting on 1 Jan 2026 ([Radiance Fields](https://radiancefields.com/platforms/luma-ai)). Postshot's Free tier is non-commercial and **cannot export PLY/SPZ splats** ([Jawset pricing](https://activation.jawset.com/shop/pricing)). Two roles are defensible. The first is a disclosed sensor logger, such as KIRI "Camera pose", Record3D, Polycam raw or NeRFCapture, feeding the team's own refinement, training and viewer. The second is a disclosed benchmark. Scaniverse's on-device mode is free and exports PLY/SPZ ([Niantic Spatial](https://www.nianticspatial.com/blog/scaniverse)), so its splat can be scored against the team's own on held-out-frame PSNR, splat count, file size and viewer fps. That comparison counts in the team's favour under "pipeline soundness". Reports conflict on whether the Scaniverse app is available on Android. Keep the shipped core permissively licensed: COLMAP, nerfstudio, gsplat, Spark and splat-transform. Avoid the original INRIA 3DGS code, whose license is non-commercial. That last point comes from the model's own knowledge and was not re-verified.

## Conclusion

The weak points in this pipeline are not the parts that look ambitious. The custom navgrid and metric-scale logic are architecturally the same thing commercial systems do. The failures will come from defaults the team inherited without choosing them: nerfstudio quietly drops loop detection and reads only the first sub-model, splatfacto grows Gaussians without a cap, and the viewer library no longer receives updates. All three are configuration and integration fixes, not research problems. That points the remaining effort toward validation. One clean recapture, measured registration counts, a single timed training run and a benchmark against Scaniverse will tell the team more than any further method switching.

The deadline also argues for small, incremental steps. Every heavier upgrade in the notes is a bolt-on that leaves a working fallback in place: COLMAP 4.x global mapping, MCMC, TSDF meshes and navmeshes. Lock in ranks 1-5 by roughly day 5, so that Round 3's unattended overnight run inherits a pipeline that has already been rehearsed on two or three spaces.
